## Disable marker reaches the real root CLI

The root `codex.exe` CLI entrypoint synchronously calls `take_remote_control_disabled_env()` before `arg0_dispatch_or_else` and before dispatching `codex app-server` (`codex-rs/cli/src/main.rs:1042-1047`). The marker is `CODEX_INTERNAL_APP_SERVER_REMOTE_CONTROL_DISABLED`; the helper accepts only the exact value `1` and removes it from the process environment (`codex-rs/app-server-transport/src/transport/remote_control/mod.rs:87-96`). The app-server subcommand passes that bool into `run_main_with_transport_options`; with `remote_control=false`, it selects `RemoteControlStartupMode::DisabledEphemeral` instead of `ResolvePersisted` (`codex-rs/cli/src/main.rs:1249-1325`). The standalone app-server binary has the same consume-and-map behavior (`codex-rs/app-server/src/main.rs:81-121`).

Important caveat: the CLI match prioritizes `remote_control=true` over the environment marker (`cli/src/main.rs:1306-1316`; standalone equivalent `app-server/src/main.rs:117-122`). The supervised launcher must own the fixed argv and omit hidden `--remote-control`; the marker alone is not a guard against that option. It should also use the root `app-server` command, fixed stdio transport, and no daemon/proxy subcommand or inherited renderer-controlled args.

## What DisabledEphemeral guarantees

`start_remote_control` maps `DisabledEphemeral` directly to `RemoteControlDesiredState::Disabled`, independent of the persisted preference (`codex-rs/app-server-transport/src/transport/remote_control/controller.rs:269-285`). The background WebSocket task is still constructed, but its loop resolves persistence only when state is `Unknown`; it then waits for state to become enabled before calling `connect` (`codex-rs/app-server-transport/src/transport/remote_control/websocket.rs:497-515,689-694`). With `DisabledEphemeral`, the `Unknown` branch is skipped and the disabled wait does not call the WebSocket connect path. This is the source-level evidence for no Remote Control startup-resolution, enrollment, listener, or network attempt in the disabled mode. No persisted preference is read or changed by this branch. Do not infer that Codex’s separate cloud-config/model-catalog startup work is suppressed; those are allowed and separately disclosed for this mission.

Stdio is single-client mode (`app-server/src/lib.rs:815-818`). A supervised Quotafern child therefore has no second RPC client that can enable Remote Control behind its guard. The fixed RPC allowlist must itself omit `remoteControl/enable`, `remoteControl/disable`, pairing, and client-management methods. Process supervision and static request allowlisting remain necessary; DisabledEphemeral is a startup mode, not a universal policy preventing another privileged caller from changing state in other transports.

## Read-only status evidence

The protocol exposes `remoteControl/status/read` as an experimental RPC with a `global_shared_read("remote-control")` serialization scope (`codex-rs/app-server-protocol/src/protocol/common.rs:1193-1198`). It requires `experimentalApi=true` on this connection; no other experimental method needs to be sent. Its handler calls `RemoteControlHandle::status()` and copies status fields into the response (`codex-rs/app-server/src/request_processors/remote_control_processor.rs:118-126`; dispatch at `app-server/src/message_processor.rs:1213-1217`). This is an in-memory read: it does not resolve persistence, open a network connection, change desired state, or write preference. `Disabled` is the required positive status; missing/malformed/other status must fail closed before `account/read` or quota.

The server also sends the current Remote Control status to a connection when it finishes initialize, then broadcasts later status changes (`app-server/src/lib.rs:1266-1280,1310-1321`). This is useful corroboration, but use the explicit read RPC as the synchronous gate. The status schema also returns server name, installation ID and optional environment ID; retain only the enum for the guard and do not surface or log the identifiers.

## Runtime guard and limits

Strongest source-supported sequence: launch the exact pinned image under the existing supervised-stdio containment with fixed `app-server --stdio` arguments and child-only marker `...=1`; omit `--remote-control`; initialize once with the needed status capability; read `remoteControl/status/read` and require exactly `disabled`; only then allow account/quota RPCs. Recheck status before each quota request and fail closed if it is not disabled; monitor the status-change notification during the session. The child is dedicated and single-client, and its RPC allowlist must never send Remote Control mutations.

Source proves the disable branch avoids the Remote Control connect path, but this report is not runtime network proof. A future owner acceptance must capture the actual child’s Remote Control network outcome separately from the expected cloud-config/model refresh and account/quota requests; the marker value and disabled status alone are not evidence that no socket attempt occurred. This reviewer did not launch the process or observe network activity.

`account/read` may do the Codex-owned workspace-routing `accounts/check` lookup on cache miss and invoke auth recovery on 401 (`codex-rs/app-server/src/request_processors/account_processor/workspace_routing.rs:250-282,356-400`). `account/rateLimits/read` is itself a Codex backend usage request (`account_processor.rs:1152-1249`). These are expected/disclosed effects of the authorized quota flow and are distinct from Remote Control network activity.

## No-credential-write constraint: blocker

This source audit does **not** support a strict promise that launching the supervised stdio server and reading quota will leave Codex credentials unchanged. `AuthManager::auth()` calls `proactive_refresh_reason()` and, when a managed ChatGPT token is in its refresh window or interval, calls the guarded refresh path (`codex-rs/login/src/auth/manager.rs:2480-2495,3300-3320`). `auth_with_http_client_factory()` invokes `auth()` (`manager.rs:2498-2504`); the required `account/rateLimits/read` handler calls that API (`codex-rs/app-server/src/request_processors/account_processor.rs:1152-1159`). Successful OAuth refresh writes the replacement access/refresh/ID tokens through `persist_tokens` (`manager.rs:3384-3424`). The RPC's `account/read` `refreshToken:false` only suppresses explicit refresh requested by that RPC; it does not disable this proactive auth behavior.

Startup cloud-config loading also launches a background refresh service (`codex-rs/cloud-config/src/bundle_loader.rs:47-58`); `refresh_cache_once()` calls `auth_manager.auth()` before fetching the remote bundle (`cloud-config/src/service.rs:544-555`). Thus even before the quota RPC, an eligible existing login can be refreshed and persisted. The refresh decision depends on credential expiration/last-refresh metadata, which this source-only review did not inspect and the task forbids reading. I found no supported pinned config/CLI option that makes these app-server auth paths read-only.

This changes the disposition above: the `DisabledEphemeral` Remote Control branch is source-supported and has no RC resolution/connect path, but **the full mission is blocked if its strict no-credential-mutation rule remains**. Fresh consent can disclose Codex-owned refresh/write behavior, but disclosure cannot satisfy a hard prohibition on credential mutation. Do not launch the actual system profile or proceed to account/quota RPC under that strict condition. A next step requires the owner to explicitly relax the no-write condition to allow Codex-managed refresh/persistence, or a different supported path whose source guarantees no auth refresh; no such path was found in this audit.

### Status interpretation caveat

A `disabled` status response is corroboration, not proof that the marker selected `DisabledEphemeral`. The `RemoteControl` watch begins with status `Disabled`, and a session built from `RemoteControlDesiredState::Unknown` also initializes its status as `Disabled` because only an enabled desired state starts as `Connecting` (`app-server-transport/src/transport/remote_control/controller.rs:80-93,269-296`). The loop may later resolve the persisted preference (`websocket.rs:497-515,602-626`). Therefore, an early status read can report disabled while persisted state is still unresolved. Prove the effective startup branch through controlled exact-image launch inputs and source-pinned mode mapping; use the initialize-time `remoteControl/status/changed` notification and subsequent status notifications as runtime corroboration, and separately capture network outcomes. The status notification is sent to an initialized connection (`app-server/src/lib.rs:1266-1280`) and later status changes are broadcast (`lib.rs:1310-1321`). `remoteControl/status/read` is experimental and requires `experimentalApi=true`; it reads the in-memory status only. A strict client can avoid enabling experimental capabilities by requiring the initial status notification and monitoring updates instead.
