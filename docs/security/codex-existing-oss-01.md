## Codex startup and transport implications

The pinned app-server protocol has public `account/read` and `account/rateLimits/read` operations. Its ordinary fresh startup is broader: it constructs `AuthManager`, starts a cloud-config fetch/refresh task and an online model-catalog refresh worker. Default `RemoteControlStartupMode::ResolvePersisted` also resolves persisted Remote Control state on stdio; an internal environment marker disables only that subsystem. There is no supported quota-only startup flag. See [the startup/security review](codex-existing-oss-01-startup-review.md) for source lines and exact-tag evidence.

The public `codex app-server proxy [--sock PATH]` subcommand proxies raw bytes to the local control socket; it is not a quota-only RPC wrapper and does not visibly perform the Windows peer verification referenced by the TUI socket helper. The server uses WebSocket over its `codex_uds` local socket abstraction on Windows. QuotaView's `codex-ipc` desktop pipe is a different channel and does not provide quota requests.

## Decision: attach only to an already-running Codex server

For Quotafern, a fresh `codex app-server` child is not an acceptable ExistingAccount implementation: it would start unrelated server work, and stdio does not suppress persisted Remote Control resolution. Use an attach-only native client if the implementation passes focused review:

- Derive only the fixed local-control endpoint for the already-selected Codex home. Require the expected private, current-user-protected socket directory and reject reparse/path substitution.
- Connect over WebSocket/UDS directly. Verify the peer PID on the connected socket, require same user and non-elevated integrity, then verify the pinned official Codex native image by exact SHA-256 before protocol initialization. Do not use `codex app-server proxy` as an opaque relay.
- Do not spawn, start, stop, or restart any Codex server. No fallback to `native.exe app-server`, CLI discovery, credential/config reads, or provider token handling.
- After fresh native consent, send only `initialize`/`initialized`, `account/read`, and `account/rateLimits/read`; enforce bounded messages, timeouts, strict request IDs, and fail closed on server requests or malformed responses. Require a present rate-limit account ID, compare it with `account/read` identity before and after the read, then publish only the sanitized snapshot. Disconnect only the client socket.
- Keep consent explicit and disclose Codex-managed auth refresh and possible credential-state writes caused by Codex's own account/rate-limit implementation. Never consume resets or request inference.

This design avoids creating new app-server startup activity; it cannot prove that an already-running daemon has no unrelated background work already underway. The owner-reported fixed endpoint exists by sanitized existence metadata only; no connection or account/runtime inspection was made for this comparison. Implementation, synthetic protocol tests, peer verification, native build, and authenticated owner acceptance remain pending.

## Focused implementation review: Windows attach path

Review disposition: no verified blocking finding in the reviewed attach-only implementation. The Windows System route branches to the existing-socket client before credential loading. It checks the selected home and protected socket directory, allows only the Windows AF_UNIX kernel reparse tag `0x80000023` for the socket entry, and verifies the connected peer via kernel peer PID, same-user/non-elevated tokens, executable path, and pinned image hash before sending RPC. Managed mode remains separate. Fresh consent precedes endpoint resolution/connection and discloses that the preexisting Codex service may perform its own background work.

Identity limitation: in the pinned protocol with experimental API disabled, `account/read` exposes ChatGPT email and plan but no workspace/account ID. The client requires `accountId` from `account/rateLimits/read`, binds it with email/plan for later refreshes, brackets each usage read with account reads, and rejects relevant account-change notifications. This binds subsequent reads to the returned quota identity, but cannot independently establish which workspace should be expected on the first read or rule out every transient workspace switch for the same email/plan if no notification is observed. Describe this as a limitation; do not claim perfect workspace-substitution detection. No source blocker was verified from this review. Runtime attach behavior remains unverified by the reviewer.

## Installed-tag startup and initialization side-effect audit

Exact source reviewed: installed tag `rust-v0.164.0-alpha.11.1` (peeled commit `6905ecede7816e91373e9eabda3f6b0368fc747b`). Disposition: these RPCs do not initiate a fresh app-server startup or change Remote Control persisted startup resolution/listener state. They are not side-effect-free. With fresh native consent explicitly covering the following Codex-owned effects, I consider the reviewed attach policy acceptable; the product must not claim that attaching changes only Quotafern-local state.

`initialize` stores `clientInfo.name` on the connection session and `experimentalApi=false` remains per-connection (`codex-rs/app-server/src/request_processors/initialize_processor.rs:119-150`; `message_processor.rs:956-969`). Since `quotafern` is not in `NON_ORIGINATING_CLIENT_NAMES` (`initialize_processor.rs:19,132`), initialization can set the process default originator if unset, updates the process-global `USER_AGENT_SUFFIX` to `quotafern; 0.1.0`, and enters first-originating-client gateway-login control logic; the implicit branch calls `allow_automatic_login` (`initialize_processor.rs:153-193`). It also calls `track_initialize`; standalone `app-server` passes `default_analytics_enabled=false` (`main.rs:124-130`), so this source alone does not establish an outbound analytics event. The client name is therefore truthful shared process metadata; do not impersonate reserved Codex client names or use private flags to avoid the effect.

Initialization completion also calls `notify_workspace_routing_to_connection`, which asynchronously runs `read_account_for_background_workspace_routing()` (`message_processor.rs:956-969, 829-841`; `request_processors/account_processor/workspace_routing.rs:204-249`). That can perform workspace routing discovery: on cache miss `read_account()` calls `BackendClient::get_accounts_check()` and has Codex unauthorized recovery available on 401 (`workspace_routing.rs:284-400`). The explicit `account/read` with `refreshToken:false` does not request refresh, but reads latest config/account state and can likewise miss the workspace routing cache and perform this lookup (`workspace_routing.rs:250-282`). `account/rateLimits/read` performs the Codex backend usage request and may use Codex-managed auth handling (`account_processor.rs:1152-1249`). The consent should therefore disclose the routing check and Codex-owned automatic authentication/recovery, as well as the requested account/quota read.

Remote Control resolution and its listener are established in app-server startup: the default runtime mode is `ResolvePersisted` (`lib.rs:488-499`, `main.rs:117-121`), and `start_remote_control` plus persisted-preference resolution occur in startup code (`lib.rs:888-928`). The local-control Unix-socket transport does not populate `app_server_client_name_rx`; only the stdio transport does (`lib.rs:815-839`). Thus this client's initialize name does not feed the persisted Remote Control startup-resolution key. The model refresh worker is constructed with the app-server message processor (`message_processor.rs:400`); startup/cloud-config and model workers are not started by these per-client RPC handlers. An already-running daemon may already have those workers and unrelated work underway; this review does not claim otherwise. The newly triggered routing lookup is the known request-time network side effect.
