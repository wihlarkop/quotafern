# F3 app-server startup security gate

Research date: 2026-10-24. This investigation uses current official OpenAI documentation and public Codex source pinned to [`rust-v0.164.0`](https://github.com/openai/codex/tree/rust-v0.164.0). No Codex executable was run, no real Codex process was started, and no local authentication files or credentials were inspected.

## Decision

There is no documented quota-only app-server launch mode in the sources reviewed. The documented `account/rateLimits/read` and `account/usage/read` RPCs are read-oriented, but selecting stdio only selects the app-server transport. It does not isolate startup from persisted Remote Control restoration, Codex cloud configuration loading and refresh, model catalog refresh, or Codex-managed token refresh. Keep Quotafern's live connection gate closed for this pinned version.

The best officially supported read-only fallback is the [Codex usage dashboard](https://chatgpt.com/codex/settings/usage). OpenAI also documents `/status` for checking remaining limits in an already-running Codex CLI session. These keep authentication within Codex and do not add quota data to Quotafern. The app-server RPCs remain a future integration option only after OpenAI documents a startup policy that suppresses the unrelated work, or the pinned implementation is changed and separately reviewed.

## Evidence

### Remote Control restoration is independent of stdio transport

- The official command reference describes `codex app-server --listen stdio://` / `--stdio` as the JSONL stdio transport and separately describes WebSocket and Unix-socket transports. The same reference characterizes app-server as primarily for development/debugging and subject to change. It documents `codex remote-control start|stop` as managing the background daemon and says that command is not a replacement for `codex app-server --listen` for local protocol clients. [App-server command reference](https://learn.chatgpt.com/docs/developer-commands#codex-app-server), [Remote Control command reference](https://learn.chatgpt.com/docs/developer-commands#codex-remote-control)
- In the pinned CLI source, the mode is `ResolvePersisted` when neither the hidden enable flag nor a disabled-start marker is present. The marker is named `CODEX_INTERNAL_APP_SERVER_REMOTE_CONTROL_DISABLED` and is explicitly described in source as an internal daemon marker. These are implementation details, not documented app-server launch controls. [CLI mode selection](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/cli/src/main.rs#L1302-L1318), [hidden CLI flag](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/cli/src/main.rs#L608-L610), [internal marker](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server-transport/src/transport/remote_control/mod.rs#L79-L96)
- The library default is also `ResolvePersisted`. The app-server creates the Remote Control manager while starting any transport. In this mode, the manager begins in an unknown state; after its client name is ready, its websocket loop resolves the saved enrollment for the current Codex account and client. If that record enables Remote Control, it waits for the enabled state and connects to the Remote Control websocket. This is conditional on a previously enabled persisted enrollment, so this does **not** mean every stdio app-server always connects. It does mean Quotafern cannot assume stdio prevents restoration or outbound Remote Control traffic. [Runtime default](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server/src/lib.rs#L493-L503), [manager startup](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server/src/lib.rs#L888-L900), [persisted startup state](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server-transport/src/transport/remote_control/controller.rs#L265-L288), [restore and connect loop](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server-transport/src/transport/remote_control/websocket.rs#L459-L515), [account-scoped enrollment lookup](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server-transport/src/transport/remote_control/desired_state.rs#L31-L88), [auth and persisted enrollment lookup](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server-transport/src/transport/remote_control/websocket.rs#L619-L645), [websocket connection](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server-transport/src/transport/remote_control/websocket.rs#L696-L772)
- `allow_remote_control` can block Remote Control when supplied as a managed requirement. That is policy enforcement, not a documented per-launch opt-out for a local quota client. [Managed requirement check](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server/src/lib.rs#L779-L799)

With `stdio://`, the RPC itself stays on the child-process pipes; the risk is the separate, possible outbound Remote Control connection after persisted state is resolved. A WebSocket `--listen` is a distinct inbound app-server listener and is not needed for the stdio client. [Transport listener branch](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server/src/lib.rs#L820-L861)

### Startup loads cloud configuration and can refresh it later

- Before serving the RPC client, the pinned app-server loads local bootstrap configuration, creates a Codex `AuthManager`, installs the cloud-config loader, and loads the effective configuration. [Cloud startup path](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server/src/config_manager.rs#L400-L418)
- The cloud-config loader starts a background task that first requests the latest bundle and then enters the cache refresh loop. On startup, `get_latest` consults `AuthManager::auth()`, checks for eligible auth, and uses a matching cache if available; a cache miss or invalid entry falls through to a remote bundle fetch. The background loop waits between refreshes and fetches again; this tag sets the normal interval to 15 minutes. [Loader task](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/cloud-config/src/bundle_loader.rs#L44-L73), [startup cache/network path](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/cloud-config/src/service.rs#L193-L226), [background refresh and interval](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/cloud-config/src/service.rs#L35-L40), [refresh loop](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/cloud-config/src/service.rs#L511-L565)
- Therefore, an existing valid cache may avoid a startup cloud-config fetch, but does not remove the cloud-config loader or the later refresh path. A quota RPC allowlist cannot constrain those startup services.

### Model catalog refresh is another startup task

- Message-processor initialization starts a model refresh worker. It calls `list_models(Online)` immediately, then repeats after 4 minutes 30 seconds. [Worker creation](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server/src/message_processor.rs#L392-L404), [worker schedule](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/app-server/src/models_refresh_worker.rs#L10-L59)
- Whether that listing makes a remote request depends on the configured model manager. A configured `model_catalog_json` is documented as a JSON catalog loaded from a path at startup; the pinned provider builder turns a supplied catalog into an in-memory static manager, whose `raw_model_catalog` returns that in-memory data. [Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference), [static catalog selection](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/model-provider/src/provider.rs#L396-L427), [static catalog result](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/models-manager/src/manager.rs#L827-L841), [Codex model refresh policy](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/models-manager/src/manager.rs#L544-L580), [refresh eligibility](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/models-manager/src/manager.rs#L687-L691)
- A static catalog is a narrow way to avoid model catalog network refresh; it does not suppress cloud-config loading, account authentication, or Remote Control restoration. It is not a quota-only mode.

### Codex-managed authentication may write refreshed credentials

- Current official app-server docs say the `chatgpt` auth mode is owned by Codex, persists tokens, and refreshes them automatically. The docs describe `account/rateLimits/read` and `account/usage/read`, but do not promise that starting an app-server performs only those reads. [Authentication modes](https://learn.chatgpt.com/docs/app-server#authentication-modes), [app-server RPC overview](https://learn.chatgpt.com/docs/app-server#api-overview-1)
- In the pinned source, the cloud-config path calls `AuthManager::auth()`. For managed ChatGPT auth, `auth()` can proactively refresh when an access token is near expiry or when the recorded refresh is older than the scheduled interval. The refresh path saves the updated tokens and `last_refresh` through the configured auth storage backend. [Auth access during cloud config load](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/cloud-config/src/service.rs#L193-L226), [automatic refresh decision](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/login/src/auth/manager.rs#L2476-L2494), [refresh conditions](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/login/src/auth/manager.rs#L3300-L3318), [persist refreshed credentials](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/login/src/auth/manager.rs#L1647-L1690)
- Official docs say Codex stores credentials in the OS keyring or `auth.json`, depending on configuration. No credential store was examined here. [Credential storage](https://learn.chatgpt.com/docs/auth#credential-storage)
- Setting `refreshToken: false` on a Quotafern account-read request would only affect that RPC's request semantics; it cannot disable the separate `AuthManager::auth()` calls during app-server startup or a later cloud-config refresh. That boundary follows from the pinned source paths above.

## Supported controls and limits

- The documented app-server command controls the protocol transport (`stdio`, WebSocket, or Unix socket); it does not document a switch to disable persisted Remote Control resolution, cloud-config loading, or background model refresh. The source-level internal marker and hidden flag are not acceptable product controls for Quotafern.
- `model_catalog_json` can suppress remote model catalog lookup when set to an authoritative static catalog, but it is insufficient to satisfy a no-unrelated-startup-activity gate.
- No user or developer action against an authenticated Codex installation was performed. These are source-derived startup behaviors; they are not evidence that any particular owner machine has Remote Control enabled, needs a token refresh, or will fetch cloud configuration on its next launch. Cache state, auth mode, account policy, and persisted enrollment determine those branches.
- No authenticated acceptance, startup experiment, CI credential access, or protocol fixture was run as part of this investigation.

## Recommended product posture

Leave the F3 live gate false. For manual quota checking, link to the official [usage dashboard](https://chatgpt.com/codex/settings/usage); for an already-running CLI session, OpenAI documents `/status`. Do not have Quotafern start app-server merely to get a quota snapshot until a supported startup policy can establish and verify that unrelated network/auth work is disabled.
